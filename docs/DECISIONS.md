# Architecture decisions

Format: date · decision · why · consequences.

## 2026-10-19 · D1 · PostgreSQL-only job queue (pg-boss + row claiming), no Redis/BullMQ

Spec allows "Redis and BullMQ or an equivalent reliable architecture".
- The send queue must live in Postgres anyway (scheduled messages are shown in the UI and must survive
  restarts). Claiming a due row and reserving quota in one transaction makes double-send and
  over-quota impossible across parallel workers; a second store (Redis) could diverge after downtime.
- One fewer stateful service to run, secure, back up and restore on the VPS and the laptop.
- pg-boss gives cron, retries with exponential backoff, singleton jobs, and dead-letter on Postgres.
Consequence: throughput ceiling is far above cold-email volumes (thousands/day per workspace).

## 2026-10-19 · D2 · npm workspaces; Next.js route handlers are the backend API

pnpm is not installed on the dev machine; npm workspaces are built in. A separate API server would duplicate
auth and validation; route handlers under `apps/web/app/api` with a shared service layer are enough.
Long-running work never runs in the web process; it lives in `apps/worker`.

## 2026-10-19 · D3 · Tests run against real Postgres via `embedded-postgres`

The primary dev machine has no Docker and no WSL. `embedded-postgres` downloads real Postgres binaries
per platform, so tests exercise real SQL (SKIP LOCKED, constraints) everywhere. CI additionally builds
and smoke-tests the Docker Compose stack.

## 2026-10-19 · D4 · Freshness gate + sticky sender instead of a boot gate
A laptop that sleeps never "boots", so gating on worker start is unsafe. A send is claimable only when its account
(and, for company-stop campaigns, every campaign account) synced within `SYNC_MAX_STALENESS_SEC`. Follow-ups always
use the step-1 account so its sync covers the lead's replies and threading stays intact.

## 2026-10-19 · D5 · Unknown send outcomes are held, not resent
"Not found in Sent" is not proof of non-delivery (SMTP append gap, index lag). After a 15-minute re-search the
message becomes HELD for a human decision. Duplicate cold emails are worse than one delayed email.

## 2026-10-19 · D6 · Attachments stored in Postgres (bytea, ≤ 25 MB)
Keeps backup/restore and local→VPS migration to a single `pg_dump`.

## 2026-10-19 · D7 · Provider caps clamped to 50 % for calendar-day accounting
Providers enforce rolling 24 h windows; usage rows are per calendar day. Clamping the effective limit to half the
provider cap makes two adjacent days unable to exceed the rolling cap. Cold-email limits (≈30/day) sit far below it.

## 2026-10-19 · D8 · Password hashing: better-auth default (scrypt)
PS-SEC-03 names argon2id; scrypt is an equally recommended memory-hard KDF (OWASP) and avoids a native dependency
that complicates Windows dev and the Docker image. Revisit only if a compliance requirement names argon2id.

## 2026-10-19 · D9 · TypeScript 5.9.3 (not 7.x)
typescript-eslint 8.72 (latest) supports `typescript <6.1.0`. 5.9.3 is the newest version satisfying both it and the
"latest 5.x" fallback in the plan. Revisit when typescript-eslint supports 7.x. ESLint 10 and Vitest 5 work.

## 2026-10-19 · D10 · Plain `fetch` for Gmail, Graph and the OAuth token endpoints
No `googleapis`, `google-auth-library` or `@azure/msal-node`. Reasons: msal keeps refresh tokens in its own cache, which clashes with our encrypted per-account store and cross-process refresh lease; the libraries retry internally, which hides the 429/5xx/timeout distinctions the send pipeline depends on (ambiguous vs transient vs rate-limited); and every call goes through one injected `fetch`, so contract tests run on fixtures. Cost: we write about a dozen REST calls and the token exchange ourselves.

## 2026-10-19 · D11 · IMAP/SMTP test servers
In-process `hoodiecrow-imap` (pure JS, scriptable) plus `smtp-server` (nodemailer's) for fast local runs on Windows; hoodiecrow 3.x is young (six releases in two days), so a Linux-only CI job runs the same contract suite against a real `greenmail/standalone` container and is required for the phase gate. Fallback if hoodiecrow does not run: an `ImapClientLike` double. Cursor-expiry tests recreate the Sent folder (INBOX cannot be deleted in IMAP).

## 2026-10-19 · D12 · Gmail scopes: `gmail.send` + `gmail.modify`
Not `gmail.readonly`. Spam rescue and mark-read (PS-WARM-08) need modify; adding a scope later forces every account to reconnect. Both are restricted-class, so a self-hosted single owner pays nothing extra. Deviates from the PROVIDER_COMPLIANCE "modify only if required" line, which is updated.

## 2026-10-19 · D13 · Token refresh by DB lease, not a lock held over HTTP
Refresh claims a lease on the account row (`refreshLeaseId/Until`, 20 s) in a short transaction, calls the token endpoint (15 s timeout) with no transaction open, then commits the new credentials if it still holds the lease. Avoids holding a pooled connection during HTTP and losing a rotated Microsoft refresh token when a transaction aborts. A refresh response without a refresh token keeps the stored one; token-server 5xx is transient, never an auth failure.
Note (P2-T02a, deviates from the brief): when the conditional write matches nothing and the stored token is still the stale one, refresh goes back to the lease/wait step (same 25 s bound) instead of returning stale creds.

## 2026-10-19 · D14 · Fake provider state is file-backed
`FAKE_MAIL_DIR` JSON files (atomic writes under a lock file), so the web server, worker and Playwright share one fake mailbox. Enabled only with `MAIL_PROVIDER_FAKE=1`, refused when `MODE=vps`.

## 2026-10-19 · D15 · User-supplied mail hosts are SSRF-guarded and TLS-only
In `MODE=vps`, IMAP/SMTP hosts resolving to loopback, private, link-local, CGNAT or ULA ranges are refused unless `ALLOW_PRIVATE_MAIL_HOSTS=1`; checked on every connect in web and worker; connect to the checked IP with SNI; AUTH only after TLS, plaintext only to loopback in local mode. The helper is reused by P7-T02 webhooks.

## 2026-10-20 · D16 · No campaign sending before P4 sync exists (lifted by P4-T05)
**Lifted by P4-T05:** mailbox sync now writes `lastSyncCompletedAt`, so the freshness gate opens for synced accounts (real providers stay gated by D17).
Nothing in Phase 3 writes `lastSyncCompletedAt`, so the claim's freshness gate keeps real campaigns from sending until P4-T05 ships. The explainer reports `sync_pending`. There is no stub: one that marked accounts fresh without reading their inboxes would send follow-ups to people who already replied. Tests set freshness with a test-only `markFresh` helper.

## 2026-10-20 · D17 · Real-provider campaign sending gated on a recorded live check
How the gate works:
- `ProviderVerification` (one install-level row per provider) is written only by `scripts/live-verify.ts`, when every step passes and `findSent` returns our exact Message-ID. A failing run deletes the row.
- The claim SQL only selects accounts whose provider is in `sendableProviders()`. That returns every provider with `MAIL_PROVIDER_FAKE=1` (which `MODE=vps` refuses), and otherwise only the verified ones. There is no override.

Limits:
- One verified host or tenant enables that whole provider kind, including relays that may rewrite Message-ID.
- Duplicates stay impossible, because an unfound ambiguous send ends HELD.
- P4 reply matching must therefore fall back to the lead address plus the thread.

## 2026-10-20 · D18 · Permanent send errors carry a scope (phase-2 gate I-8)
`PermanentSendError` gets an additive `scope: "recipient" | "account" | "unknown"`, default `unknown`. It is decided by the enhanced status code and the reply text. Policy, blocklist and spam rejections are never `recipient`, even on RCPT TO.

How each scope is handled:
- **Recipient:** FAILED, the lead STOPPED BOUNCED, and a HARD_BOUNCE suppression.
- **Account:** release, the row back to SCHEDULED, and the account PAUSED via `recordProviderError`; the lead is untouched.
- **Unknown:** FAILED, the lead PAUSED SEND_FAILED, and the account PAUSED after 3 in a row (`consecutivePermanentErrors`, reset on SENT and on resume).

The `MailProvider` interface is unchanged.

## 2026-10-20 · D19 · Spec items overridden by Global Constraints
These are not built, or are forced, because a Global Constraint outranks the spec item:
- PS-SEQ-10 "ignore account limits" is not built: it would exceed per-account allowances.
- PS-CAMP-25's List-Unsubscribe toggle accepts only `true`: every campaign email must carry the header.
- PS-CAMP-04 "Account Suspended" is shown as ACCOUNTS_UNHEALTHY, whose producer is P5-T02.

## 2026-10-20 · D20 · Removing suppressions (P3-T03)
- `GDPR_ERASURE` and `COMPLAINT` suppressions are never removable, single or bulk, API or UI. An attempt returns 409 `suppression_protected`. An erasure row holds only a hash, so removing it could only let the erased person be re-imported.
- `UNSUBSCRIBE` is removable one at a time by an ADMIN, and only with `resubscribeAttestation` (a non-empty reason plus `recipientConsent: true`). The audit row holds the hash and the attestation.
- `HARD_BOUNCE` is removable one at a time by an ADMIN with `confirm`. `NOT_INTERESTED` and `MANUAL` need ADMIN only.
- Bulk delete and "clear" touch `MANUAL` entries only, and audit a capped list of hashes plus the true count.

## 2026-10-21 · D21 · Send-state lock order (amends phase-3 I4)
Every transaction that touches send state locks `ScheduledMessage` → `CampaignLead` → `AccountDailyUsage` → `CampaignDailyUsage` → `WorkspaceDailyUsage` → `EmailAccount` → `Lead`/`Suppression`. The original I4 put `CampaignLead` after `EmailAccount`. The claim must re-check the CampaignLead under its lock before it reserves, and the planner locks CampaignLead before it writes `CampaignDailyUsage.newLeads`. Any transaction taking usage rows before CampaignLead would therefore deadlock against the planner, so the claim, the sender and the planner must all use this one order. The planner keeps its exception for new or revivable `ScheduledMessage` rows only, because no claim can hold those. The sender's hard-bounce path is a second exception (P3-T11a). `suppress()` runs after the lead's own CampaignLead lock and before the usage release, so it inserts the Suppression row and stops the address's CampaignLeads in other campaigns ahead of usage. That is still CampaignLead before usage. Two simultaneous bounces of one address in two campaigns can deadlock each other, and `withTxRetry` absorbs it. The claim takes the row's `StepVariant` `FOR SHARE` after the CampaignLead (D23 stale text); `deleteVariant` (whose FK `SetNull` locks ScheduledMessage rows after the variant), lead delete/merge/bulk (Lead before CampaignLead) and blocklist add (Suppression before CampaignLead) invert the order on user paths, so they run in `withTxRetry` too (phase-3 gate M-1).

## 2026-10-21 · D22 · Step-1 deletion and leaving a subsequence (deviations from the P3-T10b brief)
- **Deleting main step 1 moves its waiting leads instead of stopping them.** The brief routes `deleteStep` through `skipStep`, which stops a lead on main step 1 (STOPPED MANUAL) because no sticky sender exists yet. Applied to a deletion, that would stop every queued lead of the campaign and end sending silently. `skipStep(…, { keepDue: true })` (deleteStep only) therefore moves those leads to the next step, which `settle()` renumbers as the new step 1. They stay QUEUED and are routed by rotation like any new lead. A user cancel of a step-1 row (`skipStep` without `keepDue`) still stops the lead.
- **`removeFromSubsequence` stops the lead.** It does not go through `skipStep`, which would advance the lead to the subsequence's next step, the opposite of "remove". It cancels the lead's open rows and sets it STOPPED MANUAL in one transaction.

## 2026-10-21 · D23 · Sender policies (P3-T11a)
- **Deleted or unassigned sticky sender.** A follow-up must come from the lead's step-1 mailbox, so it is never re-routed. When that mailbox is deleted or no longer assigned to the campaign (phase-3 gate I-3), the planner's housekeeping cancels the lead's SCHEDULED rows and sets the lead PAUSED `SEND_FAILED`. This is reversible: reconnect the address (which revives the same account row) or re-assign it, then resume the lead. The explainer reports `sticky_account_unassigned` (informational, with the mailbox ids), so the stall is never silent. Step-1 rows have no sticky sender and keep going through the re-route pass.
- **Stale text.** Edit hooks skip rows a claim holds, so the claim re-renders the row under its lock and takes the variant `FOR SHARE`. An edit that commits before the claim is picked up, and a later edit waits for the claim. `List-Unsubscribe` headers are never stored; the sender rebuilds them on every send.
- **LOST releases nothing.** When the row's token changed, whoever changed it (a late accept or recovery) owns the reservation now.
- **Sender-side SMTP rejections are never recipient scope (round 1).** A reply to MAIL FROM or AUTH, or any reply whose text says "sender" (Postfix reports `Sender address rejected` at RCPT TO), is account scope when it is a 5.1.x on MAIL FROM and unknown otherwise. Unknown means the lead is paused, never suppressed, and three in a row pause the mailbox.
- **A late SENT never moves a closed lead.** `advance` returns unless the CampaignLead is QUEUED, ACTIVE or PAUSED, so a send that completes after a stop (manual, reply or unsubscribe) cannot enter a `completed_no_reply` subsequence.
- **The 5-attempt cap also counts 429s.** Sustained throttling FAILs the row and pauses the lead `SEND_FAILED`, which the user can retry.
- **Microsoft 365 `5.4.1 … Access denied`** is unknown scope with `countsTowardPause: false`, so it never counts toward the 3-in-a-row pause. SMTP 5.1.7 and 5.1.8 are account scope on MAIL FROM and unknown elsewhere. Any 5.7.x on MAIL FROM, AUTH or DATA is account scope even when the text matches the policy words, as the brief's `relay denied` case requires.

## 2026-10-21 · D24 · Send recovery policies (P3-T11b)
- **Lease floor 300 s.** `SEND_LEASE_SEC` (default 600) must be at least 300 unless `MAIL_PROVIDER_FAKE=1`. The 60 s send timeout does not bound the SMTP Sent-folder append or an OAuth refresh, and a lease that expires mid-send only turns a good send into UNCERTAIN noise.
- **The 24 h cap needs two failed searches 15 min apart (Revision 3; round 1).** Nothing is held by the clock alone. A `findSent` that throws (account offline, auth, provider unavailable) sets `lastSearchAt` but never `searchCount`, so the next attempt waits 15 min. When an attempt throws on a row whose `uncertainAt` is 24 h old and whose previous attempt (`lastSearchAt`) was at least 15 min earlier, the row is HELD. A machine that slept past 24 h therefore searches at least twice, 15 min apart, before anything is held, and one failed search on wake (network not up yet) holds nothing. An account that can never be searched is held at its first failed attempt after the 24 h mark, because earlier attempts already exist; that unblocks GDPR deletion. A row that is not found follows the normal not-found rule (twice, 15 min apart).
- **Found means SENT through the sender's path.** `resolveUncertain` calls `recordAccepted` with the row's own claim, so the late-accept table applies if the row moved meanwhile, and `advance` leaves a STOPPED or COMPLETED lead alone. `sentAt` is the found copy's Date, or now when the header is missing or in the future.
- **Release keeps the Message-ID and resets the search.** `releaseHeld` sets `searchCount 0`, `lastSearchAt null`, `error null`, and (amended by D25) `uncertainAt null`. The same Message-ID lets a late copy settle as a late accept (both messages are credited, I8).
- **Only an ADMIN releases a HELD row (round 1).** A release may send a second copy, so like test-send it needs ADMIN, and API keys (which act as MEMBER) get 403. Cancel and retry stay MEMBER, keys allowed. `GET /api/v1/scheduled-messages` returns `uncertainAt`, `searchCount` and `lastSearchAt`, so the releaser sees whether the row was searched and not found or held after failed searches.
- **`retryFailed` also refuses a STOPPED or COMPLETED lead (409)** and resets `claimErrors`; the claim would cancel such a row anyway.
- **Boot jobs.** `JobDef.boot` marks the jobs `startWorker` sends once after registration: `campaign-plan`, `campaign-dispatch`, `send-recovery` and (P4-T05) `mail-sync`. Their crons stay as they are.
- **Queue heartbeats.** `campaign-plan`, `campaign-dispatch`, `send-recovery` and (P4-T05) `mail-sync` use `heartbeatSeconds: 10`, and the worker runs pg-boss with `superviseIntervalSeconds: 15` and `monitorIntervalSeconds: 15` (pg-boss 12 checks heartbeats per queue on the monitor interval, 60 s by default). A stately queue allows one active job, so the active job of a killed worker used to block that queue until pg-boss expired it (15 min by default). Now the job is failed about 25 to 40 s after its worker dies (10 s heartbeat plus up to one 15 s monitor pass and one 15 s supervise tick), and a restarted worker resumes sending and recovery within a minute (E2E #15). `createQueue` does not change an existing queue, so a dev database created before this change keeps the old queue options until its pg-boss schema is recreated.

## 2026-10-21 · D25 · Phase 3 gate fixes (policies)
- **Graceful stop (I-1).** On SIGTERM/SIGINT the worker aborts a stop signal before anything else; `dispatchTick` checks it before every claim and `resolveUncertain` before every row, so nothing new is claimed and the batch in flight finishes. pg-boss then waits up to `STOP_TIMEOUT_MS` = `SEND_TIMEOUT_MS` + 30 s (90 s) before Prisma disconnects, and the compose worker's `stop_grace_period` is 100 s. A send that outlives that bound (an SMTP Sent-folder append or OAuth refresh, which the 60 s timeout does not cover) is left SENDING for recovery as before. `npm run dev` on Windows hard-kills its children, so this only holds for signal-based stops.
- **Release accepts the duplicate risk once (I-2).** `releaseHeld` clears `uncertainAt`. The released row is then an ordinary SCHEDULED row: if a later claim, edit hook or archive cancels it (dead or inactive variant, a pause, a broken template), the planner re-plans the lead's current step instead of excluding it forever, and cancel and retry keep working. The Message-ID is kept, so a late copy of the original still settles as a late accept. A HELD row cancelled by the user keeps `uncertainAt` and moves the lead past the step, as before.
- **COMPLETED campaigns resume (I-4).** `resume` accepts COMPLETED with full launch validation (and the cross-campaign clash check). Enrollment and move-to-subsequence into a COMPLETED campaign stay allowed; the leads wait QUEUED until the user resumes, and the explainer and the campaign pages say so ("Resume it to send to leads added since"). Housekeeping completes the campaign again once nothing is open. Chosen over refusing with 409 because it is one entry in the resume list and matches the product this replaces.
- **Partial RCPT rejection (M-3).** When SMTP refuses a To address but accepts a Cc or Bcc, the send is not recorded as SENT: the provider throws the refused To's mapped error (D18 scope from its RCPT reply), so a 5.1.1 stops the lead BOUNCED and suppresses it, and no follow-up goes to the Cc alone. The Cc copy was delivered and its usage is released (the row is FAILED). A 4xx on the To with an accepted Cc retries, so the Cc can receive a second copy; accepted as rarer and less harmful than mailing the Cc only. Gmail and Graph accept or refuse the whole message, so this is SMTP only. **Amended by P4-T05 (gate N-1, M7):** the provider throws `PermanentSendError("lead_rejected_partial", undefined, { scope, countsTowardPause })` instead, scope `recipient` only for a 5.1.x / 5.2.1 reply on the lead (else `unknown`), `countsTowardPause: false` for a 4xx. It is never retried (a 4xx no longer sends the Cc a second copy), and the row is FAILED with its usage committed, not released, because the Cc/Bcc copies left the account.
- **Preview never shows a live unsubscribe link (M-5).** Preview and campaign test-send both render the dead "(unsubscribe disabled in test emails)" text; the live link exists only in real sends. Campaign test-send also refuses a suppressed recipient (address or domain) with 409 `recipient_suppressed` (M-4).
- **Archive leftovers (M-7).** Every planner tick cancels SCHEDULED rows of ARCHIVED, COMPLETED or deleted campaigns (SKIP LOCKED, so a claim-held row is taken on a later tick). A planner revival resets `attempts` and `claimErrors` (M-8). The send's staleness check runs after the pre-call check, right before `provider.send` (M-2).
- **Registry.** Advisory lock 726004 is `ENROLL_LOCK` / `lockEnrollment()` in `campaigns/hooks.ts`; the open CampaignLead states are `OPEN_STATES` / `OPEN_STATES_SQL` in `campaigns/lead-status.ts`.

## Phase 4 (P4-T05)

- **Sync run.** A row lease (`syncLeaseId`, 10 min, renewed after every page; a lost lease ends the run as `skipped`), no advisory lock. Branch order (C1): `syncProgress` resumes an import; no cursor starts HISTORICAL (`now − historyImportDays`); otherwise incremental, and an expired cursor starts FULL (`min(lastSyncCompletedAt − 2 d, now − 30 d)`). An import takes `currentCursor()` before listing, lists INBOX then SENT, and on completion keeps that cursor and sets the watermark to its first run's start; the next incremental run brings it current. Each message is classified (AI hook only for REPLY/UNCERTAIN, 10 s abort, failures ignored) and stored with its stop rules in one `withTxRetry` transaction before the cursor moves past it; a P2002 against the sender's `recordOutboundMessage` reruns it as `created:false`. Before classifying, NUL bytes are stripped from every string of the message (Postgres refuses them), an invalid date becomes the run's start, a Message-ID / In-Reply-To / References entry over 998 characters is dropped (a synthetic id is used), addresses are clipped to 320 and names/subject to 998 characters (btree entry limit, gate FR I1); the classifier regexes see only the first 64 KB of the text and use bounded quantifiers (FR C1). A message that still fails to ingest fails the run, so the watermark waits; the run's `SyncRun.error` is `<code> msg=<providerMessageId>`. When the two previous runs both failed on the same message, the third stores a **header-only placeholder** (same rfc id, from/to/cc/subject/date/threading headers; no text, html or attachments; classified from subject and headers), so its stop rules still run and the cursor moves; `SyncRun.error` records `placeholder <code> msg=<id>` (gate PA #1). A placeholder that also fails fails the run as before. The AI hook is skipped for a message already stored and raced against its 10 s timeout.
- **Failures.** `AuthError` goes to `recordProviderError` (NEEDS_ATTENTION unless paused). Anything else counts `syncErrors`; at 5 the account gets `status ERROR`, `lastError {kind:"SYNC", code}` (code or class name only), shown as CONNECTION_ERROR; a caught-up run clears it back to CONNECTED. `syncDue` backs off `min(SYNC_POLL_SEC · 2^(syncErrors−1), 1800)` s and picks a run that stopped early (`SYNCING`, lease free) on the next tick. `SYNC_POLL_SEC` (default 120) must satisfy `2 × SYNC_POLL_SEC + 60 ≤ SYNC_MAX_STALENESS_SEC`.
- **Providers.** Gmail and Graph cap a `listChangesSince` page at ~20 MB of raw content like IMAP: a page cut short keeps the cursor on that page with `done` (ids already returned), so nothing is skipped or returned twice. A 400 on a Gmail history call or a Graph delta link is `{expired:true}` (I-7). Graph `@removed` with reason `changed` (moved out of Inbox/Sent) is reported in `removed` like `deleted`, so the local message gets `remoteDeletedAt`. Their `listMessages` pages are capped the same way: a cut page returns our own token (`rn-cut:` + the provider token and the ids already returned). A partial RCPT rejection (N-1) takes its scope from the shared D18 `smtpScope`. A `listMessages` page token the provider refuses (`PermanentSendError`; IMAP after a UIDVALIDITY change, `page_token_invalid`) restarts that folder from `since` once per run (M11).

## Phase 4 (P4-T04)

- **D28 · Tracking only on a reachable https base.** Pixel and click links use `https://<trackingDomain>` when the account's `trackingDomainStatus` is `VERIFIED`, else `APP_URL` when `unsubscribeMode(APP_URL) === "https"`, else nothing is rewritten (`trackingBase`). The sender adds tracking at send time (needs `env.trackingKeys`); `renderedBody` stays untracked. Tokens use the unsubscribe token format with HKDF info `rightnow-tracking-v1`, so `OLD_ENCRYPTION_KEY` must be kept 90+ days. Every open is `isEstimated`; an open or click within 10 s of `sentAt`, or from a known proxy/scanner UA, is stored with `meta.machine` / `meta.scanner` and never moves lead counters or enters an ACTIVITY subsequence. A non-machine open or click enters the first active `opened`/`clicked` subsequence only from QUEUED, ACTIVE or COMPLETED (never STOPPED or user-PAUSED, as for a reply), and never moves the counters of a soft-deleted lead (phase-4 gate).

## Phase 4 (P4-T03)

- **D26 · A reply stops the lead wherever that campaign says so.** A genuine reply from an address that is a Lead stops every open CampaignLead (PAUSED included) of that lead, and of the thread's matched lead, in campaigns with `stopOnReply` (`STOPPED REPLIED`), whichever mailbox received it and whether or not it threads. Its Event is attributed to one campaign (PS-INBOX-04). With `stopForCompanyOnReply`, the other open leads of the replying lead's non-free-mail company domain in that campaign stop `COMPANY_REPLIED`; a sender who is no lead counts only when the mail answers one of our sends, and only in that send's campaign (I8). The `enrolledAt <= message date` guard applies only to unthreaded mail; an answer to one of our sends always counts, whatever its `Date:` (I7). An auto-reply stops `AUTO_REPLIED` under `stopOnAutoReply`; otherwise an out-of-office pushes the SCHEDULED rows (`FOR UPDATE SKIP LOCKED`) and `nextDueAt` of all the lead's open enrolments in campaigns without `stopOnAutoReply` (not only the matched one) to its return date, clamped to now + 90 d; a past date changes nothing, and an OOO **without a date pushes 7 days** (M12, compliance rule 63). An unsubscribe reply runs `optOutTx` for the sender's leads and the matched lead. Order inside the ingest transaction (`applyInbound`, I1): (0) an UNCERTAIN/HELD send the message answers is locked `FOR UPDATE` (ScheduledMessage first); (1) `cancelRows`, then the CampaignLead stops; (2) subsequence entry for the matched CampaignLead (allowed from STOPPED REPLIED, never for one the user had PAUSED; blank phrases never match): the first active REPLY_KEYWORD trigger whose `phrases` occur as whole words in `stripQuoted(text)`, else the first LEAD_STATUS trigger for the newly set interest; (3) Suppression (unsubscribe, and interest −1 through `applyInterestChange`, whose 1..4 branch is never used here); (3b) the locked send settles SENT through `acceptTx` (M17; usage, EmailAccount, Lead; `advanceLead` leaves the now STOPPED CampaignLead alone), so every CampaignLead lock precedes usage and Lead; (4) the Lead: interest set directly only when it was null (`INTEREST_OF`), `replies`, `lastReplyAt`, `lastEngagement.reply`; (5) Events. Suppression is written before the Lead (I1 listed it after) because `suppress()` stops the address's CampaignLeads in other campaigns, and CampaignLead locks must precede Lead locks (D21). Counters, interest and subsequences move once per message across mailboxes: when the Event already exists only the idempotent stops run, and a twin that loses the Event insert to a concurrent transaction throws a retryable error so `withTxRetry` reruns it. A soft-deleted lead is never revived or counted.
- **D27 · Bounce classes.** HARD = enhanced status `5.1.*` or `5.2.1`, or any `5.x.x` whose text matches `/user unknown|no such user|does not exist|address rejected|invalid recipient|mailbox unavailable|recipient not found/i` and not `/spam|policy|block|reputation|blacklist|denylist|dmarc|spf|dkim/i`. SOFT = `4.x.x` or `5.2.2`. Everything else, including `5.7.*`, is UNKNOWN. The target send is found by the DSN's original Message-ID, else the newest SENT row from the receiving mailbox to the recipient (lead, cc or bcc) within 14 days. Only HARD suppresses (`HARD_BOUNCE`, source `dsn`); it stops the lead (`BOUNCED`, set before `suppress()`) only when the DSN's recipient is the lead's address, or it names none and the lead was the only recipient (I2). Otherwise only a named cc/bcc of the target send is suppressed. A DSN with no target send, or naming an address the target send never went to, records the Event only and suppresses nothing (gate PA #4, replaces M15: the From of a DSN is not authenticated, so a forged one could otherwise block any address). The Event stays on the lead with `meta.recipient`. A DSN whose target is UNCERTAIN or HELD proves the send went out and settles it SENT like a reply (M17), so Release cannot send it twice. SOFT and UNKNOWN record an Event only (input for P5 health).

## Phase 4 (P4-T06)

- **D29 · Manual replies and quota.** A reply, reply-all or forward from the inbox is not blocked by the user's daily limit (it departs from "never exceed per-account allowances" for that limit only). It is refused with 409 `provider_cap` when today's `sent + reserved + units > floor(providerCap / 2)`, where `units` is every recipient (to and cc). Every recipient is checked against the blocklist (409 `recipient_suppressed`). **Reserve first (gate PA #5, the overshoot window is closed):** before the provider call one short transaction takes the thread's reply lease (`Thread.replyLeaseUntil` = now + send timeout + 60 s, a conditional `UPDATE ... WHERE lease is null or expired`; a second concurrent reply on the thread gets 409 `reply_in_progress`) and reserves `units` on `AccountDailyUsage` with the claim's guarded upsert (`sent + reserved + units <= floor(providerCap/2)`), so neither two replies nor a reply and a campaign claim can pass the cap together. On accept the transaction that stores the OUT message moves the units from `reserved` to `sent` (campaign sends shrink to match); a pre-send failure releases them; an unknown outcome keeps them reserved (like UNCERTAIN). The lease is cleared when the call ends and expires on its own after a crash. A lease column rather than advisory lock 726005: an xact lock ends with its transaction, a session lock would need a pinned connection held across the network call, and no network call may run inside a transaction. The account-only SQL is used rather than `quota.ts` `commitUsage`/`releaseUsage`, which also write campaign and workspace usage that a reply never reserved. The OUT message is stored with the `(accountId, rfcMessageId)` find-or-create `ingestMessage` uses (M16): when sync already imported the Sent copy the reply reuses it and still counts. An unknown outcome (`AmbiguousSendError`, or any error that is not a classified provider error) is reported as 502 `send_uncertain`, stores nothing and is never retried; sync imports the copy if it went out. When the provider accepted the mail but storing it fails, the answer is 502 `sent_not_recorded` ("do not send it again"), never a plain 500.
- **Inbox views and the Others bucket.** Primary = a live (not soft-deleted) lead, an inbound message and a last inbound kind other than BOUNCE; Others = the remaining inbound threads (no lead, deleted lead, bounce). A hard-deleted lead's thread is Others too. `scheduled` lists threads of leads with SCHEDULED rows (the UI shows the P3 Scheduled view for that tab). The list is one raw SQL id query (the lead has no FK from `Thread`, so liveness is an `EXISTS`), then a Prisma fetch in that order; search is an `ILIKE` scan with `%`, `_` and `\` escaped.
- **Undoing a classifier's NOT_INTERESTED (I9).** Changing a thread's category away from NOT_INTERESTED when its `categorySource` is not `USER` (the classifier, `RULE` or `AI`, is what suppressed the address) deletes the lead's `NOT_INTERESTED` / source `status` suppression, only for an ADMIN or OWNER session (D20, gate FR M3); a MEMBER or an API key changes the category and the suppression stays. The lead's `interestStatus` is left as it is: set it back with the lead's own edit.
- **Attach-lead (M6).** Re-runs `applyInbound` for the newest inbound message with the new match, so the stops apply; when that message's Event had no lead it is attributed to the lead and to the lead's newest enrolment that predates the message, and the lead's `replies` (REPLY only) and `lastReplyAt` move once. A bounce is not re-run (it is keyed by the send it answers). `read-all` marks only that thread read (PS-INBOX-23).
- **Notes and erasure (I11).** `Note` rows (thread or lead, exactly one) are deleted by `gdprDeleteLead` (a lead's notes explicitly, its threads' notes by cascade) and re-pointed by `mergeLeads`. Erasure also deletes every message from, to or cc the address or naming it as bounce recipient (also with no `leadId`), the threads those deletions leave empty, and the events whose `meta` holds the address (raw or URL-encoded): deleted when they belong to the lead, `meta` reset to `{}` otherwise (gate FR I2).
- **List payload (gate PA #6).** `listThreads` returns the last message without `html`/`text`, with a `snippet` (its first 200 characters of `text`, cut in SQL).

## Phase 4 (P4-T07, P4-T08)

- **D30 · Safe rendering without a sanitizer library.** Message HTML is shown in an `<iframe sandbox="allow-popups allow-popups-to-escape-sandbox" srcdoc>` (no scripts, forms or same-origin). The document starts with a CSP meta `default-src 'none'; style-src 'unsafe-inline'; img-src data:` (plus `https:` after "Show images", for that message only), `<meta name="referrer" content="no-referrer">` and `<base target="_blank">`; a parsed copy drops `meta`, `base`, `script`, `link`, `form`, `iframe`, `object` and `embed` (meta refresh and a hostile `<base>` are not covered by CSP). `cid:` images are inlined as `data:` URIs on the server from stored attachment data. A plain-text toggle shows `text`. Attachment downloads always use `attachment` disposition, `nosniff` and a sandbox CSP. Link-target warnings are deferred to P7-T08.
- **D31 · Not stored as events; polling instead of push.** `scheduled` and `send_attempt` are not Events (the `ScheduledMessage` row is their record); meeting, opportunity and deal events come with P6-T01. IMAP IDLE and provider push (Gmail watch, Graph subscriptions) are not built; polling every `SYNC_POLL_SEC` (default 120) is the fallback the spec allows, and push sync is P7-T06.
