# Phase 6 — CRM & analytics: step plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A positive reply or a lead status change opens or moves an opportunity in a configurable pipeline. Opportunities carry deal value and cash collected, and are attributed to the campaign, step, variant and account of the last send. Tasks, reminders, notes and logged calls form the CRM activity history. Analytics, the dashboard and the CSV exports compute every number from stored Events and CRM rows, using the D34 bounce and complaint definitions. Warm-up and placement mail are never counted.

**Architecture:** New core modules in `packages/core/src/crm/` (`stages`, `opportunities`, `tasks`, `activity`) and `packages/core/src/analytics/` (`query`, `metrics`, `crm-report`, `accounts`, `dashboard`, `export`). The interest-to-opportunity hook runs inside the caller's transaction (manual edit, bulk set, reply ingest) as a leaf write after `Lead` (D21). Analytics is one grouped SQL statement per view over `Event`, using `GROUPING SETS` so totals and per-group rows come from the same pass. It joins `Lead` for segments and `Campaign` for status, tag and owner, and reuses `TARGETED_SQL`, `HARD_BOUNCE_SQL` and `perLead` from `deliverability/health.ts`. Opportunity, won and revenue figures read the `Opportunity` table, which always holds the current state, so a deal that is reopened is never counted twice. UI: `apps/web/app/(app)/crm/`, `analytics/` and `dashboard/` replace their EmptyStates.

**Tech Stack:** TypeScript 5.9, Prisma 7.10.1, PostgreSQL 18 (`UNIQUE NULLS NOT DISTINCT`, `GROUPING SETS`), zod 4, Next.js 16, React 19, Recharts 3.10.1 (already in `docs/STACK.md`, first installed by T04), Vitest + embedded-postgres, Playwright. Drag and drop uses native HTML5 events with a keyboard fallback; no new dependency besides Recharts.

**Spec:** `docs/IMPLEMENTATION_PLAN.md` is binding ("Phase 6 — CRM & analytics", Global Constraints, data model "CRM (P6)", E2E mapping rows 12–14). Also `docs/PRODUCT_SPEC.md` (PS-CRM-*, PS-ANALYTICS-*, PS-TRACK-01/10/11, PS-SEQ-21, PS-LEAD-04/19, PS-UI-04/07), `docs/DECISIONS.md` (D21, D26, D27, D28, D31, D34, D36, D37), `CLAUDE.md`, and the Phase 5 rulings and carry-forwards in `docs/HANDOFF.md` / `docs/REVIEW_LOG.md`. ## Global Constraints (from the master plan; every task inherits them)

- Every service read and write takes `workspaceId` and filters by it; `expectIsolated` on every new route.
- Lock order (D21) is extended, not changed: `Opportunity` and `Task` are leaf writes after `Lead`/`Suppression`, and Events stay last. No transaction locks `Opportunity` before a send-state row.
- No network call inside a DB transaction. CRM and analytics make none.
- API keys act as MEMBER. Pipeline stage configuration and CRM settings are ADMIN and session-only; everything else accepts `session-or-apikey` with scope `crm:read`/`crm:write` (new resource in `API_SCOPES`) or `analytics:read`.
- Metrics come only from stored rows (`Event`, `CampaignLead`, `Opportunity`, `HealthSnapshot`, usage rows for capacity). No synthetic or placeholder numbers (PS-ANALYTICS-17). "Sent" means "accepted by provider" and is never called "delivered". Opens are "estimated". Machine opens and scanner clicks are reported only in their own counters.
- Warm-up (`WarmupMessage` SEND/REPLY) and placement (`WarmupMessage` PLACEMENT) never become Events (D36, D37), so Event metrics exclude them by construction. Capacity reads usage rows, where placement sends count as sends, so remaining capacity is correct. A test pins both facts (T03).
- Bounce and complaint figures use `TARGETED_SQL`, `HARD_BOUNCE_SQL` and `perLead` from `deliverability/health.ts` and never re-define them: a DSN or ARF that matched no send does not count, and a lead counts once.
- Timestamps are stored in UTC. Analytics buckets in UTC by default, or in an IANA `tz` the user chooses (PS-UI-07, PS-TRACK-12).
- Every task writes its tests first, then runs `npm test`, `npm run lint` and `npm run typecheck`, all green, before committing. UI tasks also run their Playwright spec (`E2E_PROD=1` on the Windows dev machine, from `apps/web`).

## Decisions taken by this plan (record as D40–D42 in `docs/DECISIONS.md` in the task that implements them)

- **D40 · Pipeline, opportunities and the interest hook (T01a).** `PipelineStage(position, kind OPEN|WON|LOST, interestCodes Int[])`. A workspace's defaults are inserted lazily on first CRM access by `ensureStages`, which uses `createMany skipDuplicates` on `@@unique[workspaceId, name]`, so no advisory lock is needed: Not Contacted, Contacted, Replied, Interested `[1]`, Meeting Scheduled `[2,3]`, Proposal Sent, Negotiation (all OPEN), Closed Won WON `[4]`, Closed Lost LOST `[-3,-1]`. Interest codes are unique across a workspace's stages. A workspace always keeps ≥ 1 OPEN, 1 WON and 1 LOST stage, and has at most 20 stages. A stage that holds opportunities is deleted only with `moveTo`. `Opportunity` is unique per `(leadId, campaignId)` with **NULLS NOT DISTINCT** (raw SQL index in the migration; Prisma's `@@unique` would let two null-campaign rows through). One currency per workspace (`Workspace.currency`, ISO 4217, default `USD`) instead of a per-opportunity currency (deviation from the master data model: sums would otherwise mix currencies). Money is `Decimal(14,2)`, 0–1e12. `onInterestChange` runs in the caller's transaction after the Lead write. Attribution is the lead's latest ACCEPTED Event in the given campaign, else in any campaign, else none: `campaignId`, `stepId`, `variantId`, `accountId`. When a stage maps the new code, an existing opportunity of `(lead, campaign)` moves there. With none and a code in 1..4, one is created when `Workspace.crmAutoOpportunity` (default true), with `value = lead.plValue ?? campaign.plValue ?? 0`, `ownerId = lead.ownerId ?? campaign.ownerId ?? actor`, and `title = companyName || email`. Code 2 also records one `MEETING` Event per `(lead, campaign)`. Stage changes go one way only: moving a card never changes the lead's interest status, so the two cannot loop. Entering WON or LOST sets `closedAt` and records `DEAL_WON`/`DEAL_LOST` (dedupe `won:<id>:<closedAt ms>`). Leaving it clears `closedAt`. Creating an opportunity records `OPPORTUNITY` (`opp:<id>`). Stage history is the AuditLog (`opportunity.stage {from, to}`) with actor and time (PS-CRM-13). GDPR erasure deletes the lead's opportunities and tasks (FK cascade). Merge repoints them to the kept lead, and a `(lead, campaign)` clash returns 409 `opportunity_conflict` (no silent loss). The board hides opportunities of soft-deleted leads, and analytics keeps them because they happened.
- **D41 · Tasks, reminders, activity (T01b).** `Task(status OPEN|DONE|AWAITING_APPROVAL)`. A reminder is a task's `dueAt`. Due and overdue tasks, plus inbox threads whose `reminderAt` has passed, appear on the dashboard and under the CRM Tasks "Due" filter. No email or push notification. `AWAITING_APPROVAL` exists for the PS-CRM-08 view and its producers come with P7-T05; approving sets OPEN. Calls, SMS and meetings are manual log entries: `Note.kind` `note|call|sms|meeting`, on the lead. Opportunity notes are the lead's notes, so there is no second notes table. The activity feed (PS-CRM-01 "Inbox") merges the lead's notes, `REPLY` Events, and AuditLog rows `opportunity.*`/`task.*`, newest first, keyset on `(at, id)`.
- **D42 · Analytics definitions (T03).** Range = the local days `from..to` (inclusive) in `tz`, i.e. `[from 00:00 tz, to+1 00:00 tz)`, at most 400 days. **Sent** = ACCEPTED Events. **Contacted** = distinct leads with ACCEPTED of the campaign's first main step (`subsequenceId IS NULL`, minimum `order`, deleted steps included). **New leads contacted** = leads whose first ACCEPTED in the workspace is in range. **Opened** = leads with ≥ 1 OPEN whose `meta.machine` is not true. Open rate = opened / contacted, always "estimated". **Clicked** = leads with a non-scanner CLICK. Click rate = sends with ≥ 1 such click / sent. **Replied** = leads with REPLY (auto-replies counted apart, `includeAutoReplies` adds them). Reply rate = replied / contacted (`replyBase=sent`: replies / sent; the account view always uses sent). **Bounced** = hard via `perLead(HARD_BOUNCE_SQL)`, soft = BOUNCE_SOFT, unknown = BOUNCE_UNKNOWN, all under `TARGETED_SQL`. Bounce rate = hard / sent. **Unsubscribed** = leads with UNSUBSCRIBE. **Completed** = CampaignLeads COMPLETED with `completedAt` in range (campaign, day, ESP and none views only). **Meetings** = MEETING Events. **Opportunities** = rows with `createdAt` in range, plus their value. Positive reply rate = opportunities / replied. **Won / conversions** = rows in a WON stage with `closedAt` in range, plus `cashCollected`. Pipeline value = OPEN-stage rows created in range. Average deal size = won value / won. Annualized closed = won value × 365 / range days. Revenue per lead = cash collected / contacted. Conversion by stage = rows whose stage is this one or a later OPEN/WON stage, divided by all rows created in range (LOST rows count only in their own stage). Progress = (COMPLETED + STOPPED) / enrolled, the current state, from `campaignOverview`. Every unique count uses `perLead` (`COALESCE(leadId, id)`), so the events of a GDPR-erased lead still count once each. Campaign-level filters (status active = not DRAFT/COMPLETED/ARCHIVED, completed = COMPLETED/ARCHIVED; `campaignTag`; campaign `ownerId`) drop events without a campaign. PS-ANALYTICS-14 "combined score" = the D34 health score.

## Review Focus (riskiest inputs no acceptance test covers; each has a test in its owning task)

1. The same positive reply lands in two mailboxes (D26 twin), or arrives while the user sets the status by hand, or a status is set for a lead with no campaign send. The result must be exactly one opportunity per `(lead, campaign)`, including the null campaign, and one MEETING event, with no 500 (T01a `one opportunity under races`).
2. Warm-up, placement, inbox replies, test-sends, a DSN that matched no send, forged repeat bounces, machine opens and the events of a GDPR-erased lead are all present. Every metric must still equal the hand count, and placement must still lower remaining capacity (T03 `exact fixture`, `warm-up and placement never counted`).
3. An event at 23:30 UTC with `tz=Asia/Tokyo`, a DST change day, `to` before `from`, a range over 400 days, an unknown `tz`, or a `groupBy=step` view of a campaign whose step 1 was deleted. The event must land in the right bucket, the bad inputs must return 400, and nothing may crash (T03 `day buckets follow tz`, `query validation`).
4. A stage is deleted while it holds deals, the last WON stage is deleted, two stages claim interest code 1, or stages are reordered while another request moves a card. Nothing may be lost, the bad calls must return 409/400, and positions must stay 0..n-1 (T01a `stage rules`).
5. A deal goes Won → Negotiation → Won, its cash is edited after the win, or two leads with opportunities in one campaign are merged. Revenue and won must be counted once, `closedAt` must be the latest one, and the merge must return 409 (T01a `reopen and merge`; T03 `reopened deal counted once`).
