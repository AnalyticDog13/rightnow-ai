# Phase 5 — Deliverability, warm-up, re-warm-up: step plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every sending domain is DNS-checked before launch and on a schedule. Every account has a documented health score that slows or pauses it, and campaigns pause themselves on bounce waves or when all their accounts are unhealthy. Opted-in mailboxes of one owner can warm each other up honestly, and seed placement tests measure where mail lands. Idle accounts are detected inside every sync and restart at a reduced, ramping allowance that the claim enforces. Dashboards show all of it, and leads can be verified through a pluggable verifier.

**Architecture:** New core modules in `packages/core/src/deliverability/` (`dns`, `health`, `warmup`, `placement`, `lifecycle`, `rewarm`, `overview`) and `packages/core/src/leads/verify.ts`. They touch Prisma, providers, DNS and the clock only through injected `prisma`, `clock`, `providerFor` and `DnsResolver`. The re-warm and health limits are columns on `EmailAccount`, so `effectiveAllowance(a, now)` stays a pure function of the account row, and the claim, rotation, explainer, planner and API all read the same numbers (D32). Inactivity is computed inside the transaction that writes the sync watermark, so an account can never be fresh with a stale lifecycle (D33). New worker jobs: `dns-check`, `deliverability-health`, `warmup-tick`, `lead-verify`. UI: `apps/web/app/(app)/deliverability/` and the account drawer.

**Tech Stack:** TypeScript 5.9, Prisma 7.10.1, PostgreSQL 18, pg-boss 12, zod 4, Node `dns/promises` + `crypto.createPublicKey` (DKIM key size), Next.js 16, Vitest + embedded-postgres, Playwright. No new runtime dependency.

**Spec:** `docs/IMPLEMENTATION_PLAN.md` is binding (Global Constraints, Review Focus 2 and 5, "Send pipeline", "Reconciliation (P4)", P5-T01..T08). Also `docs/PRODUCT_SPEC.md` (PS-WARM-*, PS-REWARM-*, PS-ACC-11/16/24, PS-CAMP-04/27, PS-SEND-11, PS-LEAD-05/14/25), `docs/PROVIDER_COMPLIANCE.md` ("Rules our code must enforce"), `docs/DECISIONS.md` (D7, D12, D17–D31), `CLAUDE.md`, the carry-forwards in `docs/TASKS.json`, `docs/HANDOFF.md` and `docs/REVIEW_LOG.md` (Phase 3 gate M-6, N-2; Phase 4 ledger).

## Global Constraints (from the master plan; every task inherits them)

- Every service read and write takes `workspaceId` and filters by it. Worker jobs may scan across workspaces, but every write is conditional on the state it read (`updateMany … WHERE <old state>`).
- No network call inside a DB transaction (DNS lookups, `provider.send`/`locate`/`diagnostics`, verifier HTTP).
- Never exceed per account, per campaign or per workspace daily allowances. Effective account allowance = min(user limit, re-warm allowance, health throttle, ramp, `floor(providerCap/2)`); the claim, rotation, explainer, planner and account API all compute it through `effectiveAllowance`. No burst after downtime: the backlog is spread under quota.
- Lock order (D21) unchanged: `ScheduledMessage` → `CampaignLead` → usage rows → `EmailAccount` → `Lead`/`Suppression`. `Campaign` status flips, `DomainCheck`, `HealthSnapshot`, `WarmupSettings`, `WarmupMessage`, `PlacementTest` are leaf writes made after any send-state rows in the same transaction.
- Warm-up traffic is stored only in `WarmupMessage`, never in `Thread`/`Message`/`Event`, never in campaign analytics, inbox, CRM or lead counters. No fabricated engagement, no spam-folder manipulation (D36).
- Unsubscribe, hard bounce and complaint add a workspace suppression at once. "Accepted by provider" is never called "delivered"; health is "an internal indicator, not a reputation guarantee".
- Secrets only encrypted (`encrypt`, registered in `ENCRYPTED_COLUMNS` so `scripts/rotate-key.ts` rotates them). Fakes only with `MAIL_PROVIDER_FAKE=1`.
- Every task writes its tests first, then runs `npm test`, `npm run lint` and `npm run typecheck`, all green, before committing.

## Decisions taken by this plan (record as D32–D39 in `docs/DECISIONS.md` in the task that implements them)

- **D32 · Allowance state lives on the account row (T05).** Re-warm and health limits are `EmailAccount` columns, not a `RewarmPlan` table (deviation from the master data model), so `effectiveAllowance(a, now)` stays pure and every caller already passes the full row. Re-warm term (when `rewarmStartedAt` is set, whatever the lifecycle): `min(rewarmTarget, rewarmStartVolume + rewarmIncrementPerDay × priorSendDays)` where `priorSendDays = rewarmSendDays − (rewarmLastSendDay = today(account tz) ? 1 : 0)`. The ramp counts **local days with at least one campaign send**, not calendar days, so days the machine was off never grow the allowance. `recordSent` increments `rewarmSendDays` on the first send of a new local day, unless `healthCap` is set (the health hold, PS-REWARM-07). Health term: `healthCap`. Re-warm history is the AuditLog (`account.rewarm_start|complete|cancel`) plus the untouched messages, events and usage rows; `rewarmPrevious` holds what completion restores (`{ warmupEnabled }`). `dailyLimit` is never changed by re-warm.
- **D33 · Inactivity is computed where freshness is written (T05).** `computeLifecycle` runs inside the same transaction as the caught-up watermark update in `reconcileAccount`, evaluated at `now + SYNC_MAX_STALENESS_SEC` (look-ahead). After any downtime an account is stale until that transaction commits, and without downtime the look-ahead flags it before the watermark that let it send goes stale, so the first claim always sees the computed lifecycle. This replaces the master plan's "derive inactivity on the fly in `effectiveAllowance`" (same guarantee, no workspace read in five allowance callers). Idle since = `GREATEST(lastSentAt, lastWarmupAt, activityResetAt, createdAt)`. Workspace `inactivityDays` ∈ {7, 14, 30, 60}, default 30; `autoRewarm` default `AUTO`. Over the threshold, an `ACTIVE` account without a re-warm becomes: `AUTO` → `REWARMING` with a plan (`beginRewarm`), unless its latest `DomainCheck.level` is `block` → `INACTIVE`; `RECOMMEND` → `INACTIVE`; `OFF` → unchanged. `INACTIVE` sends no campaign mail (the claim's `accountOk` already excludes it) until the user chooses "Re-warm" or "Resume at full volume" (`activityResetAt = now`, audited); the explainer says so.
- **D34 · Health score and automatic actions (T02).** Rates use damped denominators: `hard% = hardBounces7d / max(accepted7d, 20)`, `soft% = (soft+unknown)7d / max(accepted7d, 20)`, `complaint% = complaints30d / max(accepted30d, 1000)`. Hard bounces = `BOUNCE_HARD` events + `SEND_FAILED` events with `meta.scope = "recipient"`. Score = 100 − min(40, 10·hard%) − min(10, 2·soft%) − min(30, 100·complaint%) − (providerErrors24h ≥ 5 ? 20 : providerErrors24h ≥ 1 ? 10 : 0) − (sync failing ? 20 : 0) − (DNS block 25 / warn 10) − warm-up spam share (T03: `round(20·spam/(inbox+spam))` when ≥ 10 measured in 14 d) − placement miss share (T04: `round(20·(1 − inbox/total))` for the latest test), clamped 0–100, shown as "internal indicator, not a reputation guarantee". Actions every 5 min: **throttle** when hard% > 2 or providerErrors24h ≥ 5 → `healthCap = max(1, floor(allowanceWithoutHealth · healthSlowdownPct/100))` (default 50); **restore stepwise** when none holds for 24 h since `healthCapAt` → `healthCap × 2`, null once ≥ allowance without health; **pause** the account when hard% > `bounceThresholdPct` (default 3, PS-CAMP-27 / Global Constraint) or complaint% > 0.1 (compliance line) → `PAUSED`, `lastError {kind:"SOFT_BOUNCE", code:"bounce_rate"|"complaint_rate"}` (display "Soft Bounce Error"), manual resume only. **BounceProtect:** campaign with `bounceProtect`, ACTIVE, ≥ 50 `ACCEPTED` in the last 24 h and hard% (same window, plain ratio) > `bounceThresholdPct`, or complaint% (30 d) > 0.1 → `BOUNCE_PROTECT`; manual resume only. **ACCOUNTS_UNHEALTHY:** an ACTIVE campaign with ≥ 1 assigned live account and none sendable (`lifecycle IN (ACTIVE, REWARMING) AND status = CONNECTED`) → `ACCOUNTS_UNHEALTHY`, and back to `ACTIVE` when one is sendable again (staleness never counts, or every wake would flip campaigns). "Account Suspended" (PS-CAMP-04) stays ACCOUNTS_UNHEALTHY (D19). Complaints come from ARF reports (`multipart/report; report-type=feedback-report`): suppression `COMPLAINT`, open enrollments `STOPPED COMPLAINED`, Event `COMPLAINT`; an ARF with no matching send records the Event only (From is unauthenticated, as for bounces).
- **D35 · DNS checks (T01).** Resolver = `node:dns/promises` `Resolver({ timeout: 5000, tries: 2 })` behind `DnsResolver`. Free-mail domains (`FREE_MAIL_DOMAINS`) are provider-managed: level `ok`, no lookups. **block** (launch refuses, no override): no SPF, more than one `v=spf1`, SPF permerror (> 10 DNS-querying mechanisms counted recursively over `include`, `a`, `mx`, `ptr`, `exists`, `redirect`), or a Gmail/Microsoft account whose SPF tree does not include `_spf.google.com` / `spf.protection.outlook.com`. **warn** (overridable with audit, as today): no DKIM key ≥ 1024 bits at the provider selectors (`google`; `selector1`, `selector2`) or common ones (`default`, `dkim`, `mail`, `k1`, `s1`, `s2`, `smtp`) or the user's selectors; DMARC missing (tries `_dmarc.<domain>` then the last two labels, `shortcut: no public-suffix list, wrong for co.uk-style domains, add PSL when one is reported`); `+all`/`?all`; MX missing; DNSBL listed; SMTP host without PTR; any lookup error other than NXDOMAIN/NODATA → `unknown` with reason "Could not check (DNS unreachable)". DNSBL: domain against `dbl.spamhaus.org`, `multi.surbl.org`; SMTP host IPv4s against `zen.spamhaus.org`, `bl.spamcop.net`, `b.barracudacentral.org`; an answer in `127.0.0.2–127.0.1.255` is listed, `127.255.255.*` (refused via public resolver) and `127.0.0.1` are `unknown`. Every reason carries a fix instruction. Results are cached in `DomainCheck`; launch, resume and re-warm always check fresh; `dns-check` rechecks daily.
- **D36 · Warm-up is a cooperative, honest peer pool (T03).** It **does**: send plain-text messages between mailboxes of the same workspace whose owner enabled warm-up on both ends, at the configured volume curve inside 08:00–20:00 account time (weekdays only if set), at least 600 s apart, never catching up a missed day; reply from the receiving mailbox to `replyRatePct` % (the receiver's setting) of received messages (decided once on receipt with `random()`, sent ≥ 30 min after receipt, never a reply to a reply); measure where each message landed (INBOX seen by sync, else one `locate()` 60 min after sending → SPAM/OTHER/MISSING). Messages say what they are: subject `[<filterTag>] Mailbox warm-up <8-hex>`, body "Automated warm-up message between two mailboxes of the same sender, sent by a self-hosted rightnow-ai installation. No action is needed.", headers `X-RightNow-Warmup: 1` and `Auto-Submitted: auto-generated`. It **does not**: open, read, mark important, star, move out of spam, mark "not spam", archive or delete anything (no write to any mailbox besides sending; D12's spam-rescue reason is not used); spin or randomise content to evade filters; mail any address outside the workspace's opted-in pool; join a third-party pool. External services plug in through `WarmupProvider` (no built-in external adapter). Warm-up volume is not campaign volume: it never touches usage rows, and its daily target is clamped to `min(50, floor(providerCap/10))`, so warm-up plus campaign stays ≤ 60 % of the provider cap. PS-WARM-08 knobs are documented in-app as "not provided" (read emulation, open rate, spam protection, mark important) or "cooperative-mailbox action" (reply rate). Sync excludes a message when its `rfcMessageId` is a `WarmupMessage` addressed to (IN) or sent by (OUT) that account: no header is trusted, so an outsider cannot hide mail by adding the header.
- **D37 · Placement tests use the owner's own seed accounts (T04).** Seeds are connected accounts of the workspace with `placementSeed = true` (opt-in, other providers give the per-ESP view); external seed addresses are not supported because their folder cannot be read. One message per seed (the chosen campaign variant rendered for a sample lead, or a given subject/body), plain sends through the tested account, stored as `WarmupMessage` kind `PLACEMENT` so sync excludes them and the warm-up checker locates them 10 min later. They count like D29 manual sends: refused (409 `provider_cap`) when `sent + reserved + seeds > floor(providerCap/2)`, else `AccountDailyUsage.sent += seeds`. The report adds the domain's DNSBL result from `DomainCheck`. SpamAssassin scoring is "not provided" (no spamd).
- **D38 · Lead verification (T08).** `EmailVerifier` returns a `VerificationStatus`. Built-in `mx` verifier: syntax invalid or no MX (NXDOMAIN/NODATA) → `INVALID`; disposable domain → `RISKY`; otherwise the status is left `NOT_VERIFIED` (an MX record proves nothing about the mailbox, so it never claims `VERIFIED`); lookup errors → unchanged. `http` verifier template: POST `{ email }` as JSON to a user https URL (`assertPublicHost`, 10 s timeout, no redirects) with `Authorization: Bearer <apiKey>`, reading `statusPath` from the JSON and mapping `valid|invalid|risky|catch_all|unknown` to `VERIFIED|INVALID|RISKY|CATCH_ALL|NOT_VERIFIED`. Config stored encrypted in `Workspace.verifierConfigEnc`. Runs as a background job (`PENDING_JOB` while queued); cost is the user's.
- **D39 · Gate carry-forwards (T02).** M-6: the claim re-checks campaign `accountTags` and ESP routing rules for **step-1 rows only** (a mismatch → CANCELLED `stale`, the planner re-routes); follow-ups stay sticky (D23). N-2: housekeeping pauses orphaned follow-up leads with the new `StopReason ACCOUNT_UNASSIGNED` and reverses its own pause (→ ACTIVE, `nextDueAt = now`) once the sticky account is live and assigned again; a migration relabels existing matching `SEND_FAILED` pauses. Cc rejection (P3-T11a): a recipient-scope `PermanentSendError` from Gmail or Graph on a row with cc/bcc is treated as unknown scope (lead paused, nothing suppressed, `countsTowardPause: false`), because the provider does not say which address failed; SMTP keeps its per-RCPT scope (N-1). Sync escalation keeps an earlier non-SYNC error in `lastError.previous` and a caught-up run restores it (`status` CONNECTED only if the restored kind is not CONNECTION).

## Review Focus (riskiest inputs no acceptance test covers; each has a test in its owning task)

1. The laptop is off 30 days (or an account sits idle past the threshold while syncing normally) → the first claim after it becomes fresh already uses the re-warm allowance, never the full limit; with `RECOMMEND` it sends nothing (T05 `fresh implies lifecycle computed`, `look-ahead flags before the watermark goes stale`; T06 downtime extension).
2. A warm-up or placement message reaches a peer that is also a Lead in a running campaign, or the peer's warm-up reply quotes it → no Thread, Message, Event, reply count or stop; the sending mailbox's SENT copy is not ingested either; a stranger's message carrying `X-RightNow-Warmup: 1` is ingested normally (T03 `warm-up never reaches the inbox`).
3. DNS is unreachable (ETIMEOUT/SERVFAIL), returns two SPF records, an include loop, or a Spamhaus "public resolver" answer → `unknown`/`fail` with a reason, never a crash, never a silent pass, never a false "listed" (T01 resolver-fault cases).
4. A bounce wave in one campaign that shares accounts with another → only that campaign goes BOUNCE_PROTECT; the accounts are throttled; a user-PAUSED campaign is never flipped; BOUNCE_PROTECT never auto-resumes while ACCOUNTS_UNHEALTHY does (T02 `campaign actions are isolated and conditional`).
5. A health breach during re-warm, the user lowering `dailyLimit` mid-plan, or resuming a paused re-warming account → the ramp holds, the allowance never exceeds `min(target, dailyLimit)`, resume returns to REWARMING, cancel/complete restore warm-up exactly (T05 `resume keeps re-warm`, T06 scenarios 4–5).
